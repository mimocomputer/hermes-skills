# Lightweight vector-score transcription

## When to Use

Use for licensed/user-supplied vector music PDFs when heavy OMR is unavailable. Load musicxml-engraving-accessibility and pdf skills as well. Do not assume a successful MusicXML import proves musical accuracy.

**Classify the source first, before any tool choice.** Check whether the PDF carries a real text/vector layer (`pymupdf`: characters with music-font names such as OpusStd/OpusTextStd, `get_drawings()` notehead and stem paths). If it does, transcribe from the vectors and **never run OMR** (Audiveris, PDFtoMusic, Soundslice import): on a vector score the glyph origins are exact, while OMR re-guesses pitch, divisi, beams and tuplets from pixels and is strictly worse — it costs hours and can be less accurate. OMR is for scans without a text layer only. Name this check in the delivery report so the choice is auditable.

**The PDF is the source of truth** — not a MusicXML/MuseScore file the user supplies. Reference exports and later MuseScore roundtrips are plausibility checks, never the reading; when a supplied file disagrees with the print, follow the print and say so explicitly.

1. Inspect PDF `pymupdf` rawdict character origins, font names and glyph counts, and `get_drawings()` paths. Persist page-wise raw characters, spans and vectors plus source PNGs before inference. Maestro often exposes noteheads `œ`, `˙`, `w`, rests `∑`, `Ó`, `Œ`, `‰`, flags `j`/`J`, dynamics `P`=mp and `F`=mf; calibrate against a rendered source, never assume another font has this mapping.
2. Detect five long horizontal staff lines and calculate half-space distance. Determine clef and map glyph **origin** y, not bounding-box center, to pitch. Note bounding boxes include font ascender padding. Assign glyphs to the nearest staff across the entire page, not just a local system: ledger notes from the previous system otherwise leak into the next.
3. Detect barlines by matching both an actual staff-top boundary and the exact bottom staff boundary. A note stem can coincidentally end at the bottom staff line; the bottom-boundary test alone creates false bars. Merge double/final strokes using calibrated source spacing, and exclude courtesy signatures after the final real measure.
   - Deduplicate touching beam polygons by their interpolated vertical level at the stem, not polygon count: a left and right beam segment can meet on the same stem without forming a sixteenth-note beam.
   - Inspect all notehead font sizes and vector-only shapes. Reduced-size noteheads can be grace notes, while circled cross half-note heads can be vector drawings absent from the music-font character census. A glyph-only total is not an ink-notehead total.
   - Use stem geometry to review ledger-note staff assignment, but do not blindly replace notehead proximity with stem-midpoint proximity: dense piano chords and cross-staff engraving can invalidate either heuristic.
4. Obtain rhythm from head shape, touching stems, flags, filled straight-sided beam polygons and augmentation dots. Cluster small x offsets in octave/chord heads, but inspect any reversed-second notes. Never infer note lengths from horizontal spacing alone.
5. Check every chord's head glyph types and distinct stems, even when its measure duration sum already looks correct. Dotted-whole chords beneath dotted-half melody notes can pass a naive measure sum test while silently shortening the chord. Separate simultaneous rhythmic layers into voices and verify each voice clock. Shared-head unisons may need two singer voices for accessibility; disclose if retained as one printed notehead.
6. Persist unresolved rhythm discrepancies and source-check them visually. Encode tuplets with real time modification. Retain actual incomplete pickup/final bars as implicit and document them; do not pad or change a signature just to make clocks fit.
7. Recover ties/slurs from filled Bezier shapes and notehead endpoints. A tie needs equal pitch AND temporal adjacency. Recover cross-system ties only when both printed curve halves agree. Keep matching evidence and flag unproofread curve associations.
8. Extract lyrics from original text spans, excluding staff labels, harmony symbols and directions. Split internal syllable gaps within a span when engraving spacing spans multiple notes. Sort raw characters by x and exclude separately drawn hyphens before reconstructing these chunks; otherwise a late-drawn hyphen shrinks the chunk bbox and joins syllables onto the wrong note. Encode Korean/phonetic rows separately and carry syllabic state across system boundaries.
9. Validate MusicXML `type`, dots and tuplet ratio against numeric duration. A missing dotted-whole duration mapping with a fallback quarter type can be accepted by MuseScore but imported as a much shorter note. Do not default unknown durations to quarter: fail visibly.
10. Import into the user's requested MuseScore version, export MusicXML again, and compare canonical part/staff/pitch/onset/duration multisets. Divisions can change on export, so normalize rational durations. Compare measure ordinal for implicit measures because MuseScore may export an internal X1 number. Render an actual PDF and visually inspect source-comparable systems.
11. Treat imported playback tempos as potentially converter defaults rather than source evidence. PDFtoMusic-based workflows have documented a default of 80 (https://github.com/stubiedoobiedoo/pdf-omr-pmerge#known-issues-and-solutions); confirm the user's version/export before asserting this universally. Inspect printed tempo, PDF metadata/attachments and the actual MusicXML metronome/sound tags separately. A plausible playback speed does not prove a tempo was encoded in the PDF.
12. Verify every source notehead is accounted for, page by page, programmatically. Separate this coverage assertion and exact roundtrip verification from an editorial accuracy claim. Report remaining lyric, curve, voice-identity and repeat-playback uncertainty honestly.

## Opus-font and export pitfalls

- Calibrate Opus separately from Maestro: OpusStd can expose sixteenth rests as `≈`, sixteenth flags as `r`/`R`, spoken cross noteheads as `¿`, and augmentation dots as OpusSpecialStd `™`. A flag origin need not coincide with the stem endpoint; inspect actual offsets. Treat cross heads as spoken/unpitched notation, not evidence of a prescribed sung pitch, and disclose any positional pitch used for MIDI.
- Preserve explicit lyric spaces as segmentation boundaries. Exclude proven tie-stop continuations when assigning a new syllable: a long, left-aligned word can otherwise map to the second tied head. Match lyric extension rules to the exact lyric baseline and text-right edge, not a loose below-staff band that also contains ledger lines.
- Inventory every source cubic curve piece. Pair both halves across system breaks, accounting for curves that end several points before a double bar; include cross-system slurs with changing pitch, not just equal-pitch ties. Stem-side slur endpoints can be substantially farther from the head than tie endpoints. Persist matches and audit unassigned pieces rather than widening tolerances without review. A clean discriminator on Sibelius output: beams, stems, barlines and crescendo wedges are drawn with straight line items, ties and slurs with Bezier items — so take only paths containing a `c` item, then match ends to notes by x inside a generous y window of the staff (slur ends sit at the note's x but clearly above or below it). Classify tie vs slur by asking the model, not the geometry: a curve joining two adjacent same-pitch notes of one voice that the model already ties is a tie; a curve joining different pitches (or same pitch without a model tie) is a phrasing slur. A slur drawn as an outline yields two curve paths, so dedupe by (page, staff, voice, bar, onset) pairs. Number the slurs per voice/staff and emit `<slur type="start|stop" number="k"/>`; then run an XML-level pairing pass per (voice, staff, number) that drops starts or stops whose partner is missing — a one-voice-per-line edition loses the partner whenever a slur spanned the two printed voices, and an unpaired slur is worse than none.
- Detect paired diagonal wedge strokes and double-bar stroke clusters explicitly; neither appears in a notehead census. A nearest-staff rule alone can misassign dynamics printed between lyrics and the following staff; source-check these exceptions.
- Respect the user's harmony-playback preference; Julian wants native Harmony playback explicitly enabled (`<play>1</play>`). Disable it only when requested or when analysis-only treatment has been agreed. Audit automatic chord-channel events separately from notated tied-note attacks, because MuseScore can synthesize hundreds of additional chord notes. MuseScore may also omit terminal silent measures; retain the untouched export as evidence, extend only end-of-track deltas to the verified score duration, and recheck note events unchanged.
- Set MusicXML page defaults and explicit credit types before relying on credit placement. Recheck the native title frame: imported poet/lyricist alignment can overlap the title even when MusicXML positions differ.
- Recover the music-font beat-unit glyph beside every numeric tempo rather than assuming quarter BPM: Maestro `h` is a half note, so half=126 requires `sound tempo=252`. A text-span split across a bar can misassign the closing tempo fragment; source-check and encode a real metronome object.
- Export long native scores one format at a time with a subprocess timeout and individual logs; an interrupted multi-output batch does not establish that its outputs exist or are valid.
- Preserve authoritative MusicXML separately when MuseScore turns `unpitched` spoken crossheads into positional pitched notes. Report this semantic roundtrip exception explicitly; notehead/onset/duration equality is not unpitched identity. Normalize documented piano voice renumbering separately from musical differences.

Native MuseScore 4 MSCZ stores its style in `score_style.mss`, not necessarily an embedded `Style` node in MSCX. To restore source hide-empty systems, read existing style properties `hideEmptyStaves` and `dontHideStavesInFirstSystem`, then change them to 1 and 0 respectively; keep parts and their rests rather than deleting music. Re-import/export after any native change and verify notes are unchanged.

Derived editions (splitting one printed staff into separate parts, transpositions, cuts) must ship under their own file name and folder, never under the source transcription's name — the user must not confuse them with the transcribed original. A requested split of a combined staff (string divisi, or two voices on one printed staff) is the documented exception in DAISY's engraving guideline G17, valid only because the user asks for it: put articulations, slurs, dynamics and texts into **both** new staves and duplicate markings that apply to the group (G19), otherwise the split makes the braille worse, not better. Keep the printed work title in the MusicXML (the work title is a core element of DAISY's Metadata Guidelines for Braille Music Scores and Music Books, 19.02.2023 — the catalogue record itself is produced separately, so the score title alone is not "the DAISY metadata") and mark the edition in `<identification><miscellaneous>`; name the delivered files after the change, e.g. `<Work>-getrennte-Stimmen.mscz` / `...-DAISY.mxl`. Tag the language of every lyric row with `xml:lang` on `<text>` (never on `<lyric>`) — DAISY metadata core element C7, "the language of any sung or spoken text within a score"; the rule and the guideline-ID map live in the musicxml-engraving-accessibility skill, file `references/daisy-guidelines-summary.md`.

One staff per voice means: one part, one staff, one voice (never voice 1 and 2 on the same staff). Splitting a printed shared staff (two noteheads on one stem = upper/lower part; a single shared notehead = both parts unisono, duplicated; rests copied into both) yields two parts with one voice each — verify 'one voice per measure' programmatically for the new parts and leave untouched parts element-identical for a fidelity claim.

Convention of the separated edition, stated by the user: a part must not sit out with rests where the section sings the same line. Where a rest of one part spans exactly a note of the other part (same onset, same length), copy that note in — no clipped or patched note values; where the parts genuinely differ, the notes differ. Every part carries the printed syllable (attach the staff's syllable to the note at that onset in each part). The faithful edition stays literal, divisi exactly as printed.

Pitfall that silently ruins a split edition: an extractor commonly stores a two-notehead divisi pair as a **chord inside voice 1** (correct for the faithful score, where the pair must stay on the printed staff). A split that only copies voice 1 / voice 2 per part therefore leaves the lower tone stuck in the 1er part and the 2er parts almost empty — the note totals look plausible while half the singers get nothing. Dissolve every chord on a choral staff when building the one-voice-per-line edition: sort the pair by pitch, upper tone to part 1, lower to part 2, carry the per-tone tie/accidental with it; keep genuinely separate voices (different stems/rhythms) as they are, and duplicate single-line passages and rests into both parts. Check the result with a per-bar pitch-multiset comparison against a reference split — and always collect primary pitch **and** chord tones on both sides: comparing only the primary pitch fabricates dozens of phantom 'divergent bars'.

Coverage proof for the faithful score: count noteheads per *printed* staff band (from the detected five-line staves, nearest staff wins) and compare with the model's notes per staff. On this work it read 1749 printed heads against 1750 model notes, which is what caught that nothing was missing; a model-derived staff band would have hidden the gap it was meant to find.

Title-frame pitfalls: a MusicXML `<movement-title>` is mapped by MuseScore's importer onto the *title* text and hides the real work title, so do not use it for edition markers (a long title also gets clipped by the frame). A hand-added VBox `Text` with style `subtitle` is drawn next to the composer block and collides with it; carry the marker as the last line of the composer credit text instead.

## Choral pages: which voice owns the printed lyric line

On a divisi staff the printed text belongs to exactly one voice: the one whose notes sit under it. Do not assign each syllable to the nearest note across all voices of the staff — that scatters a single phrase over both parts and reads as an off-by-one in the split edition. Pick the voice whose note x-positions minimise the total distance to the syllable x-positions (cap the per-syllable distance so far-away syllables do not dominate), assign inside that voice, then fall back to the remaining voices only for syllables that found no note. Verify by dumping the syllable sequence per staff against the source.

A divisi staff usually carries **two** printed text lines: the lower voice's under the staff, the upper voice's **above** the staff. Reading only the band below loses the upper line entirely — on this work the Bass 1 part came out wordless in bars 1–4 while the printed "hm" line sat above the bass staff. Collect both bands: cluster characters into physical lines by baseline y, then decide each line's owner by distance to the nearest staff edge (an own line sits 11–20 pt below its staff's bottom or above its top; the neighbouring system's own line sits 35+ pt away, so the choice is unambiguous). Below-staff line → lower voice (voice 2), above-staff line → upper voice (voice 1); apply the below lines first so a row's own syllable always wins, and only let an above line fill notes still empty. In the separated edition each row then gets its text, including where the print shows one syllable for a unison/divisi pair of both rows (copy it into the row that has none, but skip notes that are tied continuations of the previous syllable — otherwise a held note under a printed extender gets a spurious duplicate).

## Ties: repair at the XML level, not only in the model

A tie end whose start is missing is a slur curve the matcher mistook for a tie. Cleaning only the in-memory model misses pairs whose adjacency the measure/voice traversal broke (voice segments, skipped cells), and leaves stray arcs in the render. After writing the MusicXML, walk each part in document order keyed by (voice, staff, pitch): drop `<tie>/<tied>` ends with no preceding start, and restore a start when the previous note of the same pitch sits in the same slot (a real tie the model had dropped). Then assert that tie starts and ends are paired and that no measure is incomplete.

## MuseScore conversion in headless Linux

`musescore4` needs `xvfb-run -a`; `QT_QPA_PLATFORM=offscreen` fails. A plain MusicXML file that is merely *renamed* to `.mxl` stalled the import until it was killed — deliver a real compressed `.mxl` (ZIP with `META-INF/container.xml` naming the rootfile) and prove it by round-tripping it back to `.mscz`. Pack from a temp copy named after the delivered edition, not from `a.musicxml`, so the ZIP's inner name matches the file the user opens. When several conversion jobs are queued (they finish in seconds, so it is tempting to fire them off per attempt), they all write into the same `out/` paths: before delivering, confirm the timestamps and that each `.mxl` is still a ZIP — a superseded job can otherwise leave a renamed plain MusicXML or an old part layout under the final name. Strip any lingering `musescore` process with `pkill -f "[m]usescore"` alone in its own command: if the same command line also contains the bare string (e.g. a later `pgrep -c musescore`), pkill matches the shell itself and kills the run.
