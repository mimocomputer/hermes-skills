# MusicXML Engraving & Accessibility (DAISY Guidelines)

## When to Use
Use when checking, cleaning, fixing, or converting digital music notation scores (MusicXML / `.mxl` / MuseScore) for accessibility, especially compliance with the **DAISY Music Braille Engraving Guidelines** (for blind musicians, braille music translation, or screen reader usage). Also applies when comparing scanned/PDF master scores against digital MusicXML files to restore missing text, bilingual lyrics, or correct structural engraving flaws.

Unless the current request says otherwise, produce the language-tagged (DAISY) edition — and a second, source-faithful edition only when the adaptation really changes music or structure (see gate 3) — use the latest stable MuseScore 4, read the current DAISY General and MuseScore guidelines, and prioritize correctness over speed. Save the project durably under `$HOME/music-scores/<descriptive-score-name>/` (on this host that is `/home/ubuntu/music-scores/`; the old `/home/debian/...` path belonged to a decommissioned server) and deliver via Julian's ownCloud transfer folder, per work one subfolder, containing only the `.mscz`, the `.mxl` and the German report. Select vector extraction or raster OMR according to the actual source rather than blindly reusing one parser. Follow all delivery gates below; disclose blockers and do not claim unperformed proofreading, screen-reader or Braille tests.

Footnotes are part of source fidelity, not optional report material: retain their exact explanatory wording and reference markers in the original edition. In the DAISY edition, separate non-sung reference symbols from lyrics and attach the explanation to the relevant musical location as a properly encoded, navigable editorial/staff note. Metadata and the report may duplicate the explanation but must not be its only location. Keep optional lyric replacements optional; do not silently change the sung words. Verify the actual MSCZ/MusicXML and rendered output for the footnote treatment, and explicitly report any accessibility behavior not tested.

## Workflow and Delivery Gates

1. **Inspect the actual source and tools first.** Classify the PDF before anything else: `page.get_fonts()`, `get_text()`, `get_images()`, `get_drawings()` **per page**. The decisive test is the images: **one large embedded image per page means a raster scan even when fonts and a text layer are present** — an OCR layer in one generic font (Helvetica) beside a full-page image is machine-transcribed garbage ('Moster Chorole of Tampo Bay' for 'Master Chorale of Tampa Bay') and is useful only as a hint for where text sits. The converse is a true vector score: music fonts (`OpusStd`, `OpusSpecialStd`, `OpusChordsStd`, Maestro-family) plus hundreds of `get_drawings()` paths per page and zero images — that is the glyph/geometry route, not OMR, and its real text layer (e.g. PlantinMTStd) can be read directly for lyrics, chord symbols and tempo. Never conclude "no glyphs" or "vector" from the presence or absence of a text layer alone; state the measured classification before choosing a parser. A scan's detail ceiling is fixed by its embedded image — crops rendered at higher dpi enlarge the same pixels and add nothing. Read page count, text/music fonts and vector drawings; map systems, measure numbers, clefs, meters, tempo changes, solo passages and navigation before transcription. Treat example titles, instrumentation and software versions in a proposed workflow as examples, not facts about the supplied score. Verify the executable version; when the user requests latest MuseScore 4, obtain the official stable v4 release instead of substituting the Debian repository version.
2. **Choose a source-grounded extraction path.** Prefer glyph/geometry extraction for vector scores and OMR for raster scans; neither removes the need for musical proofreading. **Settle where the note base comes from before starting a raster job.** This user supplies his own OMR export (Halbestunde/MuseHub → MSCZ or MusicXML) for scanned choral scores and expects it to be the base to correct; ask for it first, and generate a local OMR only as an *independent cross-check*, labelled as such. Never let a locally produced OMR silently become the transcription basis, and never take a workflow, artifact or recipe from another agent's workspace (e.g. an OpenClaw workspace) as if it were this profile's own method — establish precedent from this profile's session history and `$HOME/music-scores/` instead, and state the provenance you are actually using. Work in small source-page blocks, preserve per-note provenance and resolve rhythm conflicts against enlarged source images before continuing. When an OMR project file accompanies the scan, validate its structure *before* reading any note: parse the native project file (not the editor's re-export) and require every voice of every measure to sum to the prevailing meter with tuplet ratios applied — an OMR file that looks over-full is usually a parser that ignored tuplets, and a genuinely broken one shows up as a short list of offending measures. Then treat its pitches as a base to correct, and record per section which bars were verified note-by-note and which were only spot-checked. See [Vector transcription and export verification](references/vector-score-transcription.md), [Raster scans and OMR correction](references/raster-scan-omr-correction.md) and `scripts/clean_crop.py` for the ordered recipes and native MuseScore details.
3. **Keep transcription and accessibility adaptation separate — but only ship what actually differs.** Before adapting, retrieve the current DAISY guidelines and read both the General and relevant editor-specific sections; the local summary is a checklist, not a replacement for the source. Apply confirmed transcription corrections to the master first, then regenerate the adaptation so corrections cannot disappear on rebuild. **Quantify the difference between the two editions before delivering both**: flatten each file to (tag, attributes, text) tuples and diff the multisets, bucketed by element. If the only differences are metadata and language tagging (`xml:lang` on `<text>`, `work`/`work-title`, encoding description, an anchored editorial note), the two files carry identical music and lyrics — say so explicitly in the report instead of presenting them as two editions, and ship only the one that is the strict superset. Produce and ship a genuinely separate second edition only when the adaptation changes musical or structural content (renumbered voices, split/shared staves, added directions, notated editorial material). Julian cannot see the markup-level difference and asked for the redundant file to be dropped. Preserve original combined staves unless splitting is requested; distinguish source-faithful chords from individually addressable singer voices in the report.
4. **Verify both structure and musical meaning.** Validate against the official MusicXML XSD and check exact measure/voice clocks. Compare editor roundtrips using part, measure ordinal, staff, onset, duration and pitch; compare lyrics using onset, text, row and syllabic value; `<text>` must never contain the syllable-separating hyphen (it belongs only in `<syllabic>`). A notehead census proves coverage, not correct pitches or phrasing. Independently review all source systems, but label broad visual review separately from a complete second note-by-note transcription. **When a subagent produced the edition, the parent re-runs the gates itself before delivering** — XSD, per-voice clock, a fresh MusicXML→MuseScore→MusicXML roundtrip, and a byte-size comparison of the uploaded files. A child's summary is a claim, not evidence.
5. **Re-render the final artifacts.** Recheck corrected locations, both ends of the piece, lyrics, page/system breaks, form labels and long navigation instructions. Verify repeat playback by exporting MIDI and comparing the unfolded measure sequence; matching visible words alone is insufficient. Follow `accessible-visual-verification` for document-boundary and clipping checks.
6. **Deliver usable files, not only a report — and only the ones that are not reproducible.** Save source evidence, rebuild scripts and their environment in a durable project directory, not an auto-pruned cache. **Delivery set = the `.mscz` + the `-DAISY.mxl` + the German report.** The `-DAISY` marker is a **content** marker, not an edition marker: it belongs on the MusicXML/MXL, which is the only file carrying the DAISY language tagging and editorial metadata, and must be left off the MSCZ, which carries none of it. A second, source-faithful edition — produced only when it differs musically — is `<Work>-Originalgetreu.*`. Upload to Julian's ownCloud transfer folder (share link, write access; helper `~/.hermes/scripts/oc_upload.sh`) in a per-work subfolder — no ZIP bundles, no chat attachments, no duplicate editions. The helper builds the request URL from the path you hand it, so a folder name containing a space must be passed URL-encoded (`Grace%20Kelly`); `--mkdir`, `--ls` and `--rm` take the same path form, and `--ls` with no path lists the share root. Do not label the MSCZ "DAISY": verified, its `.mscx` contains zero `xml:lang`/`lang` occurrences in either edition (the two differ only in internal IDs and the `workTitle` meta tag), and MuseScore's own export from it would drop the tags anyway. Those two formats are the irreplaceable ones: the MSCZ alone carries the native style/layout/playback state (not reproducible from MusicXML), and the MXL alone carries the DAISY language tagging and editorial metadata (MuseScore's own export drops them, so pack it from the authoritative MusicXML). PDF, MIDI and the uncompressed `.musicxml` are derivatives — keep them in the project directory as control artifacts and upload them only on request. **When a delivery is renamed or replaced, upload the new name first, confirm its remote size equals the local byte size (PROPFIND `getcontentlength`), and only then delete the superseded name** — a mis-derived local path once produced `PUT 000` for every upload while the deletions went through, briefly emptying the folders. A `PUT 201` is not proof of delivery; the size comparison is. Recommend the native MSCZ for MuseScore editing and distinguish technical checks from unperformed NVDA/Braille-converter testing. Do not claim full DAISY conformance or editorial perfection without the corresponding tests.

**Order of work for a scan-plus-OMR job — do not invert it.** Classify the source → validate the OMR structure programmatically → build the corrected MusicXML and render it → compare the render against the scan system by system → fix → re-render → package. Reading every measure out of crops before a corrected edition exists is the failure mode: coordinate bookkeeping consumes the session and the deliverable slips, while a rendered score set beside the scan exposes octave shifts, displaced barline content, shifted lyric syllables and dropped accidentals far faster. Deep verification is welcome — Julian explicitly prefers precision over speed — but it must be visible: announce this sequence and hand over an intermediate artifact (first render, first bundle) instead of reporting only at the end.

## Core Principles & DAISY Guidelines Checklist

The DAISY Engraving Guidelines guide structurally accessible master scores and reliable MusicXML export for Braille music or Modified Stave Notation conversion. Applying a checklist does not establish successful assistive-technology use; verify actual exports and disclose which conversion and screen-reader tests were performed.

### 1. Structure & Layout (DAISY G1, G17, M1–M2)
- **Score Metadata:** Ensure `<work>` and `<work-title>` plus source-attributed `<creator>` credits are present, including the arranger when credited. Do not invent lyricist or translator identities or roles merely to fill a metadata checklist.
- **Part and Staff Labels:** Every staff/part must be correctly labelled (`<part-name>`, `<part-abbreviation>`) in the score's original language (e.g. "Sopran und Alt", "Klavier" / "S. A.", "Pno.").
- **Upbeat / Pickup Measures (Anacrusis):** An incomplete opening measure must be designated with `implicit="yes"` in `<measure>` so bar numbering matches the published print edition exactly. Never introduce fake full time signatures for pick-up bars.

### 2. Lyrics & Syllabic Structure (DAISY G12)
- **Lyric Text vs. Musical Directions:** Never place musical directions (tempo markings, dynamics, agogic instructions like `rit.`, `a tempo`, `Largamente`) into `<lyric>` tags. They must be encoded as `<direction>` with `<words>` or `<dynamics>`.
- **Syllabification:** Every syllable must have its `<syllabic>` element set properly (`begin`, `middle`, `end`, `single`). Missing or broken syllabic tags corrupt word grouping in braille music.
- **Hyphenation & Melismas:** Extended notes on a syllable must use `<extend />`. Notes sung on the same syllable across pitches (melismas) must be connected with `<slur>` to ensure the braille translator assigns the syllable to all constituent notes.
- **Never put the hyphen in the lyric text.** The syllable-separating hyphen is expressed only by `<syllabic>`; `<text>` must hold the bare syllable. MuseScore draws the hyphen itself from the flag, so a literal `-` in `<text>` shows up as an extra dash and corrupts braille word grouping. OMR output frequently copies the printed hyphen into `<text>` – audit every lyric for it and repair by stripping the hyphen and re-deriving `<syllabic>`; see [Lyrics: syllabic markup and the literal-hyphen defect](references/lyrics-syllabic-hyphens.md).
- **Multiple Languages / Strophes:** Distinguish verses and languages using the `number` attribute in `<lyric number="1">` (e.g. primary language / verse 1) and `<lyric number="2">` (e.g. secondary language / translation), rather than intermingling them in arbitrary voices.
- **Printed verse numbers:** keep the number out of the sung text. `<lyric number="N">` selects the verse row, while the printed number itself belongs in `<verse>` — MuseScore 4 imports it and renders it before the first syllable, so `<text>` stays a clean word for the braille translator. OMR output instead glues it into the text as `"1. Lo"`; split it, then number rows by the printed verse number rather than by row order, so a strophe sung to a repeated section carries its own number.
- **Silent Voices:** Do not copy lyrics into accompanying staves or voices that do not actually sing words (e.g. homophonic choral accompaniments humming or singing neutral vowels).
- **Shared choir text:** A source can print shared words only below the upper choral staff. Include them in a lower singing part at confirmed matching syllable onsets, but never on its rests or during a different text/vowel passage. Normalize lyric row numbering across systems, because geometric extraction can shift Korean/phonetic rows when adjacent text appears.
- **Language schema:** Put `xml:lang` on the MusicXML lyric `<text>` element, not on `<lyric>`; the latter is rejected by the MusicXML 4.0 XSD. Validate against the official schema after adaptation.

### 3. Directions & Dynamics Placement (DAISY G2, G3, G13)
- **Hierarchy:** System text first, staff text second, dynamics last.
- **Keyboard / Grand Staff:** Hairpins or dynamics between two staves should be attached to the upper staff (unless completely resting) and positioned appropriately, avoiding hidden auxiliary notes or voices that trigger false collision warnings in braille transcribers.

### 4. Technical MXL/MusicXML Handling
- `.mxl` files are standard zip archives containing `META-INF/container.xml` pointing to the root `.xml` score (typically `score.xml`).
- To inspect or edit programmatically:
  ```python
  import zipfile
  with zipfile.ZipFile("score.mxl", "r") as z:
      z.extractall("extracted_score/")
  # Edit extracted_score/score.xml ...
  with zipfile.ZipFile("repacked.mxl", "w", compression=zipfile.ZIP_DEFLATED) as z:
      z.write("extracted_score/META-INF/container.xml", "META-INF/container.xml")
      z.write("extracted_score/score.xml", "score.xml")
  ```

## Pitfalls
- **Missing `<backup>` doubles every measure length.** When generating MusicXML by hand or by conversion, a `<backup>` of the full measure is mandatory before the *second and later staff of the same part*, not only between voices of one staff. Without it MuseScore serialises the staves in time, computes `len="6/4"` for what should be a 3/4 bar and silently doubles the whole score (playback gaps plus wrong pagination). Symptom in the native MSCZ: every `<Measure>` carries a `len` attribute and the exported MIDI is exactly twice the expected length. Verify by re-exporting MusicXML from the MSCZ and summing each voice per measure.
- **Derive pitch spelling from MuseScore `tpc`, never from the MIDI number.** Using `pitch % 12` emits A# where the source has Bb, which adds a spurious sharp to every flat-scale note. MuseScore's tpc map: C=14 D=16 E=18 F=13 G=15 A=17 B=19 naturals; Bb=12, Eb=11, Ab=10, Db=9, Gb=8, Cb=7; F#=20, C#=21, G#=22, D#=23, A#=24. Compute `step`/`alter` from tpc and the octave as `(midi - alter - semitone(step)) // 12 - 1`.
- **The printed verse number has no MusicXML home.** MusicXML 4.0 `<lyric>` allows only `syllabic`/`text`/`elision`/`extend`/`laughing`/`humming` — a `<verse>` child is not in the XSD (nor does MuseScore round-trip it). Keep the sung `<text>` clean (never a hyphen, never the digit) and carry the verse identity in `lyric@number`; explain the printed "1."–"4." in the report instead of corrupting the syllable.
- **`<direction staff="N">` is invalid — `staff` is a child element** placed after `direction-type`/`offset`/`voice` and before `sound`. Likewise `<clef>` must precede `<staff-details>` inside `<attributes>`, and `<staff>` inside `<note>` must precede `<notations>` and `<lyric>`. XSD validation catches all three.
- **Automated OMR / Scans:** Scores converted via optical music recognition (Scan-to-MusicXML) frequently dump expressive tempo text (like "poco rit." or "a tempo") directly into lyrics of nearby notes. Always audit `<lyric>` text content against a whitelist of musical direction terms.
- **Audit OMR lyrics letter by letter — automate it.** Reconstruct every sung word by concatenating syllables in musical order up to each `begin`/`single` flag, then run the word list through `hunspell -d de_DE -i UTF-8 -l` (install `hunspell hunspell-de-de`). This catches dropped umlauts and confusable letters (König→"Konig", Chören→"Choren", Strömen→"Stromen", mächtigen→"mich-ti-gen", dein→"drin", kann→"kran.", Lobgesang→"Leb-ge-sang", hören→"hor-en", erhält→"halt", vergiß→"gill", Adlers→"Adelers") in seconds. Expect false positives: archaic verb forms (Lobet, Kommet, Lasset), pre-reform spellings (vergiß, daß) and dictionary gaps (sichtbar) — whitelist them rather than "fixing" them. Merged words in the output (e.g. "Wieesdir") are themselves a finding: they mean `syllabic` flags are missing or mis-assigned.
- **Merging two independent reads of the same measures.** Measured (Another Day of Sun, T. 41–64 read twice): the readers agreed on syllable text but differed in apostrophe style (typewriter vs typographic), in `syllables_over_melisma`, and in whether a printed hyphen sits at the end of one measure or the start of the next. Take the TEXT from the more complete reader (typographic apostrophes when the print uses them), but the melisma indices and the leading hyphen from the **union** — a held-note marker one reader omitted is usually real ("can-yons", "low,", "thing" were only marked by one of the two). Then carry `<syllabic>` across barlines: a hyphen printed at the START of a measure means the previous measure's word is still open, so the first syllable there must be `end` (or `middle`), never `single` — "bal"…"lads" and "ba"…"yoo." were otherwise split into two words. Report the number of doubly-read measures as a measure of confidence.
- **Key syllabic reconstruction by (staff, measure, verse row, onset).** Keying by the lyric's index inside its `<note>` collides when a measure carries several lyric rows, so every syllable of a row silently inherits the last computed flag (all `begin`, or all `single`). The audit above is the regression test that exposes it.
- **Verify the actual MuseScore binary:** Run `mscore --version` / `musescore3 --version`; the `mscore` command can still be MuseScore 2 even when a newer version was expected. DAISY M2 calls for at least MuseScore 4.0.2. For requested latest v4, query official `musescore/MuseScore` GitHub release assets, choose host architecture, and verify the asset SHA-256 before execution.
- **Headless MuseScore execution:** Older versions often work with `QT_QPA_PLATFORM=offscreen`. Recent Studio AppImages may still select XCB despite that variable; use `xvfb-run -a /path/to/AppRun ...` and install `xauth` plus reported missing libraries. On Ubuntu 26.04 ARM (this host) the Studio 4.7.5 AppImage at `~/.local/bin/musescore4` additionally needs `libpipewire-0.3-0t64` and `libxcb-cursor0`; with those installed, `xvfb-run -a ~/.local/bin/musescore4 -o out.<ext> in.musicxml` renders PDF, MSCZ and MIDI (verified 2026-10-12, re-verified 2026-10-15 including a real MusicXML→PDF render). Both the AppImage symlink and the unpacked `squashfs-root/AppRun` work under `xvfb-run -a`; invoked **without** a display both abort with a core dump. Do not diagnose that abort as a broken FUSE mount and do not switch to a workaround path on that basis. **Exit code 40 means MuseScore could not open the input** — when a batch of conversions that worked minutes earlier suddenly fails, check that each input path still exists (a sibling process may have moved or deleted it) before you question the install, the launcher or the file format, and never rebrand such a failure as "MuseScore cannot open this format" without re-testing with the file proven present.
- **MIDI length is not the notated length.** MuseScore's MIDI export trims trailing silence, so a final bar written as (chord + long rest) yields a MIDI shorter than the bar count × meter suggests. Before declaring a short or faulty final bar, read the final measure's actual note and rest durations in the MusicXML — not the MIDI duration. Extract an AppImage using `--appimage-extract` for FUSE-free server operation, keep the extracted directory with its launcher, and test an actual MusicXML-to-PDF and MSCZ conversion; `--version` alone does not verify rendering.
- **A roundtrip note comparison must ignore rests and `<voice>`.** MuseScore materialises whole-measure rests for staves that are empty in a MusicXML measure and renumbers voices on import, so counting every `<note>` and keying on `<voice>` makes a correct file look wrong; compare the *pitched* multiset per (measure, staff, duration-in-quarters, pitch) and keep lyrics as a separate (measure, staff, verse, text, syllabic) multiset.
- **Wedges need an explicit stop or MuseScore silently drops the hairpin.** Measured (Grace Kelly): a MusicXML carrying 21 `<wedge type="crescendo|diminuendo"/>` start tags and **zero** `<wedge type="stop"/>` elements produced a native MSCZ with **0** `<HairPin>` objects — every hairpin was lost without any error, while its 93 `<dynamics>` came through fine. Always emit start/stop pairs (`<wedge type="stop" number="1"/>`, stop at the next barline meaning the beginning of the following measure — a stop at the same measure's end produced 30-measure nonsense spans). Then verify the *native* file, not the MusicXML: count `<HairPin>` and `<Dynamic>` inside the delivered `.mscz` (`.mscx`) and require the hairpin count to match the print; a build that renders dynamics correctly can still have zero hairpins.
- **A printed "swung" marking does not swing playback — the score style does.** Measured (Grace Kelly, print "Moderately, swung ♩ = 120"): the MSCZ carried that text as a `<Tempo>` object, yet every eighth pair played straight (MIDI offbeat at 0.75 s / 1.75 s at quarter=120, identical in every bar), because `score_style.mss` had `<swingUnit></swingUnit>` (empty = off). MuseScore only swings when the score carries a swing setting. Fix without touching music or layout: set `<swingUnit>eighth</swingUnit>` and `<swingRatio>60</swingRatio>` (percent; 60 = 3:2 = MuseScore's default) in `score_style.mss`, then **prove it** by exporting MIDI and checking that offbeat onsets moved from 0.5×beat to swingRatio/100×beat. Do not "fix" this with a visible Swing text when the print has no such marking — the style value is invisible and survives a MSCZ round-trip (verified). Also measured: MuseScore 4.7.5 **ignores** the MusicXML `<swing>` element on import (in the 4.1-draft schema it is a child of `<sound>`, not of `<direction-type>`), so an MXL alone always plays straight; say which file is playback-correct.
- **Placing directions, wedges and system text by hand: five measured traps.** (1) A global cursor over a measure's children puts a direction in the *wrong voice* as soon as the measure holds a `<backup>` — the piano's left hand restarts at tick 0, so a hairpin meant for beat 3 landed mid-left-hand and MuseScore dropped a neighbouring hairpin. Walk the target voice's own block (notes of that voice, stop at the `<backup>`). (2) **Beat numbers are 1-based, onsets 0-based**: a wedge end at beat 4 must be inserted at onset 3, not 4 — off-by-one silently moved every hairpin end a beat late. (3) **Give every hairpin its own `<number>`** (MusicXML caps the value at 16, so cycle 1–16 per part): consecutive wedges on one staff that share number 1 make MuseScore merge/drop one — measured 38 hairpins where the print has 39. (4) **System text only draws reliably on the score's first staff**: attached to a middle staff MuseScore sometimes renders it nowhere, while attached to staff 1 it appears even when that staff is hidden by `hideEmptyStaves` — so put tempo/rehearsal/performance text on staff 1 and accept the print's per-staff placement as a documented deviation. (5) The MusicXML importer **replicates** system text/rehearsal/tempo onto several staves; dedupe natively (keep one per measure/marking, drop the rest) or the render shows each marking three or four times.
- **Repeat playback verification:** Do not trust MusicXML `<sound segno/dalsegno/tocoda/coda>` attributes to survive MuseScore import. Studio 4.7.5 can turn these into plain StaffText and drop repeat behavior. Inspect the native Marker/Jump objects, restore palette-equivalent objects if needed, and verify an actual MIDI export against the expected unfolded measure order. Measured example (Grace Kelly, 72 written bars, D.S. al Coda 38→13, Coda at 39): MIDI exported from the delivered **MSCZ** = 176.0 s (87 unfolded bars), while re-importing the delivered **MXL** into MuseScore and exporting gave only 146.0 s — the jump survives as native Marker/Jump inside the MSCZ, not through the MusicXML's `<sound>` attributes. Consequently the MSCZ is the playback-correct file: tell the user that editing a re-imported MusicXML loses the coda jump, and re-check the unfolded length after any MXL round-trip. Native system markers need explicit `track=0`; if appended after a polyphonic measure, the reader can assign track 1 and ignore the segno for playback. Preserve a separate authoritative MusicXML when editor export drops language/editorial metadata.
- **Metric modulation:** Inspect enlarged symbols directly for notehead fill, flags and augmentation dots before accepting a reviewer’s reading; a missed flag changes the relationship and can silently alter playback. MusicXML `sound/@tempo` is quarter-note BPM. Encode both the printed relationship and its numeric playback consequence in the original master and adaptation, while retaining any independently printed absolute tempo. Use descriptive words plus one metronome value, not duplicate numeric prose.
- **Vector-PDF transcription:** Inspect music-font glyph coordinates and drawing paths before installing heavy OMR. Vector PDFs can retain noteheads, rests, staff lines, stems, beams and ties independently. Tesseract handles text, not reliable musical recognition. Check every measure's durations and compare rendered notes to source images; structural validity alone does not establish musical accuracy.
- **Raster scans — fix the optics before reading a note.** Scan overlays are the usual killer: threshold each crop (keep ink only below roughly 150–170 grey, everything else white) so grey vendor watermarks and show-through drop out; that is what makes small noteheads and accidentals legible. Size every reading crop near the vision downscale limit (~1 megapixel) — one to three measures across the full system width at 400–500 dpi, or a single staff at 800–1200 dpi; a wider crop is silently downscaled and its ledger lines and accidentals become unreadable. Read measure numbers from the printed page, never from the OMR's own layout.
- **Locating staves and barlines in a scan.** Staff lines are rows whose dark pixels cover ~45%+ of the page width; five evenly spaced rows are one staff and consecutive staff groups are one system — record those line rows, because every crop, pitch mapping and barline search depends on them. A barline is a column whose ink is continuous across the *whole* system (top line of the upper staff to the bottom line of the lower staff); a vertical run confined to one staff height is a note stem, and a cheap row-threshold search returns stems and beams by the dozen. Pixel notehead detection (horizontal erosion, ellipse template correlation) gives objective pitch-class evidence, but staff-line removal splits noteheads that sit on a line and text or clefs produce false positives — corroborate with it, never transcribe from it alone.
- **MuseScore 4 layout control.** Reproduce the printed engraving scale with `<defaults><scaling>` in the MusicXML (10 tenths = one staff space; a 1.27 mm printed staff space is `millimeters 5.08 / tenths 40`) and confirm it by measuring the rendered staff-line spacing rather than trusting the import. Empty staves are hidden through the score style inside the `.mscz` (`score_style.mss`): `<hideEmptyStaves>1</hideEmptyStaves>` with `<dontHideStavesInFirstSystem>0</dontHideStavesInFirstSystem>`. **Hiding is per part, not per staff, and the first system keeps its empty staves anyway**, so a multi-staff part can never reproduce a print whose staff count varies per system — see [Raster scans and OMR correction](references/raster-scan-omr-correction.md) § 8 for the measurement and the two workarounds (split the part, or shrink `<defaults><scaling>` and report the scale deviation). The legacy `measureSpacing` key does not change how many measures fit per system in 4.7.5 — force the printed breaks with `<print new-system/new-page>` first, and where the spacing engine still re-breaks, the spec-supported next lever is explicit `measure/@width` values, not further blind spacing tuning.
